## 第 0 章 · 先搞清楚你要做什么

### 0.1 这 6 周要交付什么

做一个**能在 STM32F407 上实时运行的语音关键词唤醒模型**，并给出一份完整的性能报告。

完整闭环是这四个环节：

```
  训练            量化              部署              剖析
PyTorch  ──▶  INT8 TFLite  ──▶  F407 固件  ──▶  延迟/内存/功耗报告
 FP32           20 KB               实时推理          可写进简历
```

**这四个环节缺一不可。** 只做训练，那是算法工程师的活；只做部署，那是嵌入式工程师的活。
**能把两头接起来的人，就是「边缘 AI 部署工程师」——这个岗位值 30–55K。**

### 0.2 验收标准

| 指标 | 目标 | 在哪一步检查 |
| --- | --- | --- |
| 浮点测试准确率 | **> 95%** | 第 3 章 |
| INT8 后准确率 | **> 92%** | 第 5 章 |
| INT8 模型体积 | **< 80 KB** | 第 4 / 5 章 |
| 板端推理延迟 | **< 30 ms** | 第 8 周（第 5–6 周部署后） |

这四个数字记下来，面试时能直接报。

### 0.3 三件必须先知道的事

**第一，会下载约 2.3 GB 数据集。**
Google SpeechCommands v0.02，是一次性的。建议在晚上或不用电脑时挂着下载。
如果你的网络不好，第 3.1 节有手动下载的办法。

**第二，全程用 CPU 训练。**
模型只有 21,830 个参数，CPU 完全够用。30 轮大约 1–3 小时（取决于 CPU 核数）。
不需要显卡，也不需要 CUDA——这一点对业余时间推进很关键。

**第三，第 2 章的冒烟测试不能跳过。**
它只要 5 分钟，但能提前暴露 90% 的环境问题。
跳过它，你可能会在下载完 2.3 GB、训练到第 10 轮之后，才发现某个环节是坏的。

## 第 3 章 · 下载数据集并训练（约 1–3 小时）

### 3.1 数据集下载

**自动下载**（推荐）：直接跑训练命令，首次运行会自动下载。

**手动下载**（网络不好时用这个方法，可以断点续传）：

1. 浏览器打开：<https://storage.googleapis.com/download.tensorflow.org/data/speech_commands_v0.02.tar.gz>
2. 下载完成后，在 `01-stage0-tinyml\data\SpeechCommands\` 下解压
3. 确认解压后的路径是：
   ```
   data\SpeechCommands\speech_commands_v0.02\
   ├── yes\
   ├── no\
   ├── up\
   ├── down\
   ├── _background_noise_\
   └── ... (共 35 个单词目录)
   ```

**数据集概况**：105,829 条 1 秒语音，35 个单词，约 2.3 GB。
我们只用其中 4 个关键词的全部样本，加从其余 31 个词里采样的「未知」类。

### 3.2 训练

```powershell
.\venv\Scripts\Activate.ps1
python src/train.py
```

**推荐的第一次训练**（先少跑几轮，确认一切正常）：

```powershell
python src/train.py --epochs 5 --num-workers 0
```

确认没问题后，再跑完整的 30 轮：

```powershell
python src/train.py --epochs 30
```

**常用参数**：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--epochs` | 30 | 训练轮数。30 轮通常够了，多了会过拟合 |
| `--batch-size` | 128 | 内存不够就降到 64 或 32 |
| `--lr` | 3e-3 | 学习率。震荡不收敛就降到 1e-3 |
| `--num-workers` | 4 | Windows 下报多进程错误就设 0 |
| `--seed` | 42 | 随机种子，保证可复现 |

### 3.4 训练过程中你会看到什么

训练曲线保存在 `runs\<运行名>\curves.png`，三张图：

1. **Loss**：训练损失持续下降，验证损失先降后平。
   - 如果**验证损失开始上升而训练损失还在降** → 过拟合了，见第 6 章
2. **Accuracy**：两条曲线都上升，验证准确率最终稳定在 95% 以上
   - 如果**训练准确率 99% 但验证只有 85%** → 过拟合
3. **Learning rate**：先线性升温（warmup 3 轮），再余弦退火到接近 0

### 3.5 验收标准

✅ 测试集准确率 **> 95%**
✅ 参数量约 21,830，INT8 体积 **< 80 KB**
✅ 训练曲线没有明显的过拟合（训练/验证曲线间距 < 5%）

### 3.6 出错怎么办

| 报错 | 原因 | 修复 |
| --- | --- | --- |
| 下载中断 / `ConnectionResetError` | 网络不稳 | 删除 `data\` 目录重跑；或用 3.1 的手动下载 |
| `文件NotFoundError: 未找到背景噪声目录` | 数据集解压不完整 | 删除 `data\` 重新下载 |
| 训练极慢（一轮 > 10 分钟） | `num_workers` 在多进程上卡住 | 先用 `--num-workers 0` 测试；确认瓶颈后调回 4 |
| 内存不足 / `RuntimeError: out of memory` | batch_size 太大 | `--batch-size 64` 或 32 |
| 准确率卡在 20-30% 不涨 | 学习率问题或数据没加载对 | 见第 6 章 |

## 第 4 章 · 评估与剖析（约 20 分钟）

### 4.1 目的

拿到比「总准确率」更有信息量的三个东西：
- **混淆矩阵**——看出模型把哪一类判错了
- **业务指标**——关键词召回率、误唤醒率
- **算力剖析**——MACs、体积、理论延迟

### 4.2 评估命令

```powershell

```

> 把 `<运行名>` 换成实际的目录名，比如 `runs\20260901-020000\best.pt`。
> 不知道目录名就执行 `ls runs\` 看一眼。

  注：FA 指把静音/未知词判成 4 个关键词之一的比例，直接决定误唤醒次数。

### 4.4 怎么读这张表

**看混淆矩阵的对角线和最暗的格子。** 最关键的两处：

1. **`_unknown_` 那一行**：这 800 个「其他词」被判成了什么？
   如果大量流向 4 个关键词，说明模型太容易误唤醒。
2. **`_silence_` 那一行**：静音被误判成关键词的比例，这就是**误唤醒率的直接来源**。

**业务指标的两个数字比总准确率重要**：

| 指标 | 含义 | 用户体验 |
| --- | --- | --- |
| 关键词召回率 | 说了关键词，模型认出来的比例 | 低了 = 叫不应，用户最恼火 |
| 误接受率 FA | 没说关键词，模型却触发的比例 | 高了 = 乱触发，用户第二恼火 |

> 面试时讲这两个指标，比只讲「准确率 95%」专业得多。

**看各层占比能读出两条有用的信息：**

1. **stem 层占 28.8%，是最贵的单层。** 因为它在最大的输入尺寸（49×10）上做 5×5 卷积。
   这条规律在几乎所有 CNN 上都成立——**第一层通常最贵，优化时优先看它**。
2. **4 个 DS 块的 pointwise（1×1）卷积合计占 62.4%。** 这些是纯矩阵乘法，
   正好是 CMSIS-NN 优化最好的部分，所以 INT8 能拿到接近理论的加速比。

算力只有 0.70 MMACs，意味着**推理本身不是瓶颈**——
按最保守的 1.5 MAC/cycle 算也只有 2.76 ms。
真正的开销在 MFCC 特征提取（约 3–5 ms）和内存搬运上。
这个结论会直接影响第 6 周的优化方向：**别优化卷积，去优化前端和内存布局。**

### 4.6 三个要记住的数字

| 数字 | 值 | 用途 |
| --- | --- | --- |
| 参数量 | 21,830 | 模型规模 |
| 算力 | 0.70 MMACs | 决定推理延迟 |
| INT8 体积 | 20.2 KB | 决定能不能塞进 Flash |

注意 **BatchNorm 的 1,152 个参数在量化时会被折叠进卷积**，
所以实际部署体积是 20.2 KB 而不是 21.3 KB。面试时说 20.2 KB 更准确。

### 4.7 验收标准

✅ 总准确率 > 95%
✅ INT8 体积（折叠 BN 后）< 80 KB
✅ 关键词召回率 > 90%，误接受率 < 10%

前两项是硬指标，第三项是软指标——如果第三项不达标，说明数据配比需要调整，见第 6 章。

## 第 5 章 · 量化导出 INT8（约 30 分钟）

### 5.1 目的

把 FP32 模型转成 INT8，得到能在 MCU 上高效运行的 `.tflite` 文件和 C 数组。

### 5.2 先理解三件事（这一章的核心知识）

**① 为什么要量化？**

| | FP32 | INT8 | 收益 |
| --- | --- | --- | --- |
| 权重体积 | 85.3 KB | 21.3 KB | **4 倍** |
| 算力需求 | 1x | **4–8 倍**（SIMD 一条指令算 4 个 int8） | 关键 |
| 内存带宽 | 1x | 4 倍 | 在 MCU 上往往是真正的瓶颈 |
| 功耗 | 1x | 显著降低 | 电池设备的核心指标 |

**② PTQ 和 QAT 的区别**

| | PTQ（训练后量化） | QAT（量化感知训练） |
| --- | --- | --- |
| 做法 | 训练完直接转，用代表性数据集校准激活值范围 | 训练时在前向传播里插入伪量化节点，让模型「知道」自己要被量化 |
| 成本 | 几分钟 | 需要重新训练（几小时） |
| 精度损失 | 通常 1–3% | 通常 < 1% |
| 什么时候用 | **默认先用这个** | PTQ 掉点超过 3% 才考虑 |

**③ 为什么激活值需要「代表性数据集」校准？**

权重的范围好办——直接看权重的最大最小值就行。
但**激活值是输入相关的**，你不知道推理时会遇到什么数值范围。

解决办法：拿几百条**有代表性的真实样本**跑一遍前向，统计每一层激活值的实际分布，
用这个分布来确定量化参数（scale 和 zero_point）。

> **这就是「代表性数据集」（representative dataset）这个名字的由来。**
> 面试高频问题。答案要点：**它必须来自真实数据分布**。
> 用随机数据校准，会导致某些层的范围被严重低估，量化后精度崩塌。

### 5.3 导出走的是哪条路（以及为什么）

这里有一个**必须说明的技术决策**，因为它和大多数教程不一样。

#### 路线 A：ai-edge-torch（官方推荐，**但现在是坏的**）

PyTorch → `ai-edge-torch` → TFLite。这是 Google 官方的 PyTorch 直转 TFLite 工具，
看起来最正统。但 2026-09-01 实测，在 Python 3.13 / Windows 上，
它的**所有版本都无法安装**：

| 版本 | 锁死的依赖 | 结果 |
| --- | --- | --- |
| 0.7.2 | `litert-torch` → `litert-converter` | 无 Windows 发行版 |
| 0.6.0 | `ai-edge-tensorflow==2.21.0.dev20250818` | 该开发版已从 PyPI 下架 |
| 0.5.0 | `tf-nightly==2.20.0.dev20250515` | 该 nightly 已从 PyPI 下架 |
| 0.4.0 | `tensorflow==2.19.*` | py3.13 上无可用版本 |

#### 路线 B：ONNX 中转（能跑，**但我们也没用**）

```
PyTorch  →  torch.onnx.export  →  onnx2tf  →  TFLite Converter  →  INT8 .tflite
```

这条路技术上可行，我一开始也是这么计划的。放弃它有两个原因：

**原因一（技术）：自动转换器的错误是静默的。**

如果 onnx2tf 在某个算子上做了等价变换——比如把 depthwise conv 拆成别的形式，
或者改了 padding 语义——转换依然会"成功"，产出一个**能跑但精度已经崩掉**的模型。
你要到部署到板子上才会发现，而那时候已经分不清是量化的问题还是转换的问题。
排查成本极高。

**原因二（工程）：onnx2tf 的依赖树会拖垮环境。**

实测记录（2026-09-01），一条命令：

```powershell
pip install tensorflow-cpu onnx onnx2tf
```

引发的连锁反应：

```
onnx2tf  ->  onnxruntime==1.26.0
         ->  onnxsim==0.6.5
         ->  onnxoptimizer==0.4.2
         ->  onnxscript==0.6.2  ->  onnx_ir<2,>=0.1.15
```

pip 在**依赖解析阶段**耗时 **41 分钟仍未完成**；期间触发了
torch / numpy / matplotlib / scipy / scikit-learn 的**大规模卸载重装**，
卸载完成后卡死，最终整个虚拟环境报废，只能删掉重建。

为一个用不上的工具付出这个代价，不值得。

#### 路线 C：Keras 重建 + 权重搬运 + 数值验证（**本仓库采用**）

```
PyTorch 训练
     |
     |  1. 用 Keras 手工重建结构完全一致的模型
     |  2. 逐层搬运权重（做维度转置）
     |  3. 喂同样的输入，比对两边输出的逐元素误差  <-- 关键
     v
Keras 模型  ->  TFLite Converter  ->  INT8 .tflite
```

第 3 步是整个方案的灵魂。如果最大误差 < 1e-3 且预测类别一致率 > 99%，
就能**确定**转换是 100% 正确的。于是后面如果量化掉点，
就只会是量化本身的锅，排查范围直接缩小一个数量级。

维度转置对照（PyTorch 是 NCHW / OIHW，TensorFlow 是 NHWC / HWIO）：

| 层类型 | PyTorch 权重形状 | Keras 权重形状 | 转置 |
| --- | --- | --- | --- |
| Conv2d | `(C_out, C_in, kH, kW)` | `(kH, kW, C_in, C_out)` | `.transpose(2,3,1,0)` |
| Depthwise | `(C, 1, kH, kW)` | `(kH, kW, C, 1)` | `.transpose(2,3,0,1)` |
| Linear | `(C_out, C_in)` | `(C_in, C_out)` | `.transpose(1,0)` |
| BatchNorm | gamma/beta/mean/var | 同名，直接复制 | — |

**这条路线的代价**：模型结构改动时，Keras 侧要同步改，维护成本略高。
对我们这个只有 5 种算子的 DS-CNN 来说，这个代价很小。

> 三条路线走下来的经验，值得记住：
> **"官方推荐"不等于"当前可用"**（路线 A 的教训），
> **"能跑通"也不等于"该用"**（路线 B 的教训）。
> 选型时先花 10 分钟做一次 `pip install --dry-run`，
> 比读完文档再发现装不上要省事得多。

**所以最终依赖只有一样：`tensorflow-cpu`。不需要 onnx，不需要 onnx2tf。**
如果将来确实想试 ONNX 中转，请**单独**建一个虚拟环境，不要和训练环境混在一起。

### 5.4 导出命令

```powershell
python src/export_tflite.py --ckpt runs\<运行名>\best.pt
```

**常用参数**：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--n-calib` | 300 | 代表性数据集样本数。掉点多就加大到 500–1000 |
| `--per-channel` | 开 | 逐通道量化。加 `--no-per-channel` 切到逐张量做对比实验 |
| `--float-io` | 关 | 保持输入/输出为 float32，只量化权重和中间激活 |
| `--no-int8` | 关 | 只导 FP32，用于对比 |

**做对比实验的例子**（第 3–4 周的主要工作）：

```powershell
# 逐通道 INT8（默认，部署用这个）
python src/export_tflite.py --ckpt runs\<RUN>\best.pt --name int8_pc

# 逐张量 INT8（对比用）
python src/export_tflite.py --ckpt runs\<RUN>\best.pt --name int8_pt --no-per-channel

# 校准集规模对比
python src/export_tflite.py --ckpt runs\<RUN>\best.pt --name int8_c100 --n-calib 100
python src/export_tflite.py --ckpt runs\<RUN>\best.pt --name int8_c1000 --n-calib 1000
```

### 5.5 产出文件

```
export\
├── kws_dscnn_fp32.tflite      FP32 模型（对比用，排查「转换」问题时必看）
├── kws_dscnn_int8.tflite      INT8 模型（部署用）
├── kws_dscnn_int8.h           C 数组头文件（第 5 周烧进固件）
├── kws_dscnn_int8.cc          C++ 源文件（部分工具链需要）
├── export_report.json         导出报告（体积、量化参数、数值验证结果）
└── eval_kws_dscnn_int8.json   评估脚本产出的报告
```

**`export_report.json` 里的 `verify` 字段**记录了数值一致性验证的结果，
这是判断「转换是否正确」的唯一依据：

```json
{
  "verify": {
    "max_abs_diff":    3.1e-06,
    "mean_abs_diff":   4.2e-07,
    "rel_diff":        1.8e-06,
    "pred_agreement":  1.0
  }
}
```

判定标准：`max_abs_diff < 1e-3` 且 `pred_agreement > 0.99`。
不满足的话 `export_tflite.py` 会**直接中止**，不会产出一个疑似正确的模型。

**`export_report.json` 里的两个数字，第 5 周部署时一定要抄下来：**

```json
{
  "input_quantization":  {"scale": 0.0234, "zero_point": -12},
  "output_quantization": {"scale": 0.0039, "zero_point": -128}
}
```

这是模型输入/输出的量化参数。MCU 端算出 MFCC 特征（浮点）之后，
必须用它把浮点特征转成 int8 才能喂给模型：

```c
// 部署时的量化公式（记下来，第 5 周直接复制）
int8_val = round(float_val / scale) + zero_point;
```

**漏掉这一步的典型症状**：板子上准确率只有 20–30%，而 PC 上验证是 95%。
这是 TinyML 部署最常见的坑，没有之一。

### 5.6 验证量化效果

导出后**必须**验证 INT8 模型的准确率，这是最容易出问题的一步：

```powershell
python src/evaluate_tflite.py --tflite export\kws_dscnn_int8.tflite
```

这个脚本会用 `tf.lite.Interpreter` 加载 INT8 模型，在真实测试集上跑一遍，
输出和 `evaluate.py` 同样的混淆矩阵和业务指标。

**更推荐带 `--compare-ckpt`**，它会在同一批样本上同时跑 FP32 原模型和 INT8 模型，
直接把对比结果打出来，不用你手动对两个数字：

```powershell
python src/evaluate_tflite.py --tflite export\kws_dscnn_int8.tflite ^
       --compare-ckpt runs\<运行名>\best.pt
```

输出长这样：

```
  量化前后对比（同一批样本）
============================================================
指标                          FP32        TFLite          变化
--------------------------------------------------------------
总准确率                     96.20%       95.10%       +1.10%
关键词召回                   95.80%       94.60%       +1.20%
误接受率 FA                   3.10%        3.90%       +0.80%
平均置信度                    0.911        0.894       -0.017
--------------------------------------------------------------
  预测结果一致率 : 97.30%（3,892/4,000 条结果相同）
```

脚本会按下面的标准自动判定，你照着它给的指引排查即可：

| 掉点 | 判定 | 建议动作 |
| --- | --- | --- |
| < 1% | 通过 | 可以进入部署阶段 |
| 1% – 3% | 可接受 | 若 FA 同时上升，优先增加校准样本数 |
| > 3% | 不合格 | 见下方排查顺序 |

**排查顺序（很重要，别跳步）**：

1. **先跑 FP32 的 `.tflite`** 做对照。如果 FP32 tflite 也掉点，
   说明问题在「转换」不在「量化」——回到 5.3 看 `verify` 字段。
2. 看**输入饱和率**。如果 > 0.1%，说明真实 MFCC 超出校准量程被截断，
   增加 `--n-calib` 到 1000 重新导出。
3. 看**预测一致率**。如果总准确率掉点小但一致率 < 95%，
   说明大量样本处在决策边界上，实际部署会不稳定。
4. 以上都试过仍然掉点，才考虑 QAT（量化感知训练）。

### 5.7 填这张对比表（第 3–4 周的产出）

| 模型 | 体积 | 准确率 | 相对 FP32 掉点 |
| --- | --- | --- | --- |
| FP32 | 85.3 KB | ____ | — |
| INT8（PTQ，逐通道，300 条校准） | 约 21 KB | ____ | ____ |
| INT8（PTQ，逐张量，300 条校准） | 约 21 KB | ____ | ____ |
| INT8（PTQ，逐通道，100 条校准） | 约 21 KB | ____ | ____ |
| INT8（PTQ，逐通道，1000 条校准） | 约 21 KB | ____ | ____ |
| INT8（QAT，逐通道） | 约 21 KB | ____ | ____ |

**逐张量 vs 逐通道**的区别：
- **逐张量（per-tensor）**：整个权重张量共用一套 scale。简单，但某一层里如果不同卷积核的数值范围差异大，小范围的核会被量化得很粗糙。
- **逐通道（per-channel）**：每个输出通道一套 scale。精度更高，CMSIS-NN 支持。**默认用这个**。

**校准集规模那一组实验最能说明问题。** 如果 100 条和 1000 条的结果差不多，
说明你的激活值分布很稳定；如果差很多，说明分布尾部有长尾，
需要更多样本才能覆盖——这个观察本身就是面试里能讲的东西。

### 5.8 验收标准

✅ INT8 模型体积 < 80 KB
✅ INT8 准确率 > 92%
✅ 掉点 < 3%

如果掉点超过 3%，见第 6 章。

## 第 6 章 · 准确率不达标怎么办

按这个顺序排查，**不要一开始就加层数**。

### 6.1 第一步：先确认不是 bug

```
检查清单：
□ 训练集准确率和测试集准确率差多少？
    - 都低（< 60%）  → 模型或数据有问题，看 6.2
    - 训练高测试低   → 过拟合，看 6.3
    - 都高但 < 95%   → 模型容量不足，看 6.4
□ 混淆矩阵里最差的是哪一类？
    - _unknown_ 最差 → 正常，这是 6 分类里最难的一类
    - 某个关键词最差 → 可能是该词样本太少或发音相似
```

### 6.2 训练/测试都低于 60%

大概率是数据或学习率问题：

| 调整 | 做法 |
| --- | --- |
| 降低学习率 | `--lr 1e-3` 甚至 `3e-4` |
| 检查学习率是否卡在 warmup | 看 `curves.png` 的第三张图，正常应该先升后降 |
| 关掉 label smoothing | `src/config.py` 里 `TrainConfig.label_smoothing = 0.0` |

### 6.3 过拟合（训练 99%，验证 85%）

| 调整 | 做法 | 说明 |
| --- | --- | --- |
| 加大 dropout | `ModelConfig.dropout` 0.2 → 0.4 | 最直接 |
| 加强数据增强 | 提高 `DataConfig.noise_prob` 到 0.9，或把 `min_snr_db` 降到 -5 | 更难的噪声环境 |
| 加强 SpecAugment | `freq_mask_param` 4→6，`time_mask_param` 8→12 | 遮挡更狠 |
| 加大 weight decay | `--weight-decay 1e-3` | 抑制权重过大 |

### 6.4 模型容量不足（训练/验证都卡在 93–95%）

| 调整 | 做法 | 代价 |
| --- | --- | --- |
| 加宽通道 | `ModelConfig.width_multiplier` 1.0 → 1.5 | 参数量 ×2.25 |
| 加一个 DS 块 | `block_channels` 加一个 64，`block_strides` 加一个 (1,1) | 参数量 +4.6K |
| 提高 MFCC 分辨率 | `n_mfcc` 10 → 20，`n_mels` 40 → 64 | 输入尺寸翻倍，算力大增 |

> **加宽通道是最划算的。** 从 1.0 到 1.5，参数量到 49K，INT8 约 48 KB，
> 仍在 80 KB 预算内，通常能换来 1–2% 的准确率。

### 6.5 量化掉点超过 3%

| 原因 | 排查方法 | 修复 |
| --- | --- | --- |
| 代表性数据集不具代表性 | 校准样本是否来自真实测试数据 | 用测试集的真实样本做校准 |
| 校准样本太少 | 300 条通常够 | 增加到 500–1000 |
| 某一层激活值范围异常 | 看 `export_report.json` 里各层的 scale | 对该层跳过量化，或用 QAT |
| 模型本身对扰动敏感 | 看 `evaluate.py` 输出的置信度均值 | 如果 < 0.8，说明模型不够自信，先回到 6.4 提升模型 |
| 归一化没折叠进模型 | 检查 `ModelConfig.fold_norm_into_model` | 必须为 `True` |

**最后一招：上 QAT。**
在训练时插入伪量化节点，让模型学会适应量化误差。
代价是要重新训练几小时，但通常能把掉点压到 1% 以内。

## 第 7 章 · 排错速查表

| 症状 | 原因 | 修复 |
| --- | --- | --- |
| `Activate.ps1 无法加载` | PowerShell 执行策略 | `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` |
| `No module named 'torch'` | 没激活 venv | `.\venv\Scripts\Activate.ps1` |
| `No module named 'config'` | 在 `src/` 目录下运行了脚本 | 回到 `01-stage0-tinyml` 目录运行 |
| `RuntimeError: An attempt has been made to start a new process...` | Windows 多进程问题 | 加 `--num-workers 0` |
| 训练卡住不动 | DataLoader 多进程死锁 | `--num-workers 0` |
| 下载中断 | 网络不稳 | 删 `data\` 重跑，或手动下载（3.1 节） |
| `out of memory` | batch_size 太大 | `--batch-size 64` |
| `未找到背景噪声目录` | 数据集不完整 | 删 `data\` 重新下载 |
| 准确率停在 16.67% | 忘了关 `--smoke` | 去掉 `--smoke` 参数 |
| 训练很慢 | CPU 核数少 / 多进程开销 | 先 `--num-workers 0`；慢是 CPU 训练的常态，挂机跑 |
| 导出的 tflite 转不出来 | 算子不支持 | 检查是否用了非标准算子；本模型只用了 Conv/BN/ReLU/AvgPool/Linear |
| `AttributeError: module 'profile' has no attribute 'run'` | **项目里有个文件叫 `profile.py`，和标准库同名** | 已修复：剖析脚本改名为 `benchmark.py`。<br>如果你自己新建了 `profile.py` / `types.py` / `json.py` 之类的文件，<br>**立刻改名**——它们会遮蔽标准库，报错信息还特别难懂 |
| `pip install` 卡住几十分钟不动，然后 `import torch` 报 `module 'torch' has no attribute '__version__'` | **pip 正在卸载并重装核心包，中途卡死**，<br>环境已被破坏成半删除状态 | 不要再等。**只能重建环境**：<br>`rm -rf venv` → 重新 `python -m venv venv` → 重装依赖。<br>预防见下方「环境事故复盘」 |
| `onnx2tf` 安装引发 `onnxruntime` / `onnxsim` / `onnxscript` / `onnx_ir` 一大串下载 | onnx2tf 的依赖树极深 | **不要装它**。本路线用 Keras 重建，只需要 `tensorflow-cpu`。<br>若确需 ONNX 中转，单独建一个虚拟环境 |

#### 环境事故复盘（2026-09-01，真实发生过）

我在搭建时执行了 `pip install tensorflow-cpu onnx onnx2tf`，
pip 卡在依赖解析阶段 41 分钟，然后开始**卸载 torch / numpy / matplotlib /
scipy / scikit-learn**，卸载完就没动静了。环境最终报废，只能删掉重建。

识别方法（中途发现的）：

```
$ python -c "import torch; print(torch.__version__)"
AttributeError: module 'torch' has no attribute '__version__'

$ ls venv/Lib/site-packages/torch/__init__.py
（不存在 —— 已被 pip 删除）
```

三条经验：

1. **只装用得上的东西。** 这个事故里 `onnx` 和 `onnx2tf` 从头到尾没被任何代码引用过。
2. **装大依赖时分批。** 先装训练栈并验证 `import torch` 成功，再装 TensorFlow。
   这样出问题时能立刻定位是哪一批引入的。
3. **看到 pip 开始卸载你已经装好的核心包，立刻 `Ctrl+C`。**
   这时环境已经在被破坏，继续等待的期望收益是负的。 |

## 第 9 章 · 术语表

| 术语 | 全称 | 含义 |
| --- | --- | --- |
| **KWS** | Keyword Spotting | 关键词唤醒，从连续音频里检测特定词 |
| **MFCC** | Mel-Frequency Cepstral Coefficients | 梅尔频率倒谱系数，语音识别的经典特征 |
| **DS-CNN** | Depthwise Separable CNN | 深度可分离卷积网络，MobileNet 的基础块 |
| **MAC** | Multiply-Accumulate | 一次乘加运算。1 MAC = 2 FLOPs |
| **PTQ** | Post-Training Quantization | 训练后量化，训练完直接转 INT8 |
| **QAT** | Quantization-Aware Training | 量化感知训练，训练时模拟量化误差 |
| **Per-channel** | — | 逐通道量化，每个输出通道一套 scale |
| **Per-tensor** | — | 逐张量量化，整个张量共用一套 scale |
| **Representative dataset** | — | 代表性数据集，用于校准激活值量化范围 |
| **Scale / Zero-point** | — | 量化参数：`real = scale * (int - zero_point)` |
| **CMSIS-NN** | — | ARM 为 Cortex-M 优化的神经网络内核库 |
| **SpecAugment** | — | 对时频图做随机遮挡的数据增强方法 |
| **SNR** | Signal-to-Noise Ratio | 信噪比，dB 越大语音越清晰 |
| **FA rate** | False Accept rate | 误接受率，没说关键词却触发的比例 |
| **BN folding** | BatchNorm folding | 把 BN 的参数合并进相邻卷积层，推理时省掉 BN |
