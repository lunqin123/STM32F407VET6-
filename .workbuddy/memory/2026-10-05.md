### 约束与经验
- **保持行首形式不变是解析前提**：得分点必须 `①` 开头、追问必须 `→` 开头、加分/减分必须 `**★加分` 开头。
  以后手改题库要沿用这套行首格式，否则脚本会漏。
- **题号不补零**：正文里有大量交叉引用（"见 Q59"、"接 Q35"），补零会全部失效。
- **Write 工具写入含中文引号的 Python 字符串会被转成 ASCII 引号** → 直接 syntax error。
  教训：脚本里中文引语一律用「」不用 ""。
- Bash 环境缺 coreutils：`dirname`、`wc`、`head` 都不可用 → 这类统计要用 Read/Grep 替代。

## 项目整理并推送（29 个积压提交一次性入库）

推送卡了 4 次才成功，根因值得记：**全局 `~/.gitconfig` 里的 `http.proxy=127.0.0.1:7897`
（Clash Verge 默认端口）在代理软件未运行时是死地址**，而环境变量里的代理
（`127.0.0.1:60216`）才是活的 —— 两套代理配置互相打架，git 只认 global 那份。
- 症状谱系：`Failed to connect ... over proxy` → `CONNECT tunnel failed, 502` →
  `Recv failure: Connection was reset`。三种报错同源，别误判成"凭证问题"或"仓库太大"。
- 正确解法：**不动 global**（那是用户主动设的，可能只是当时没开 Clash），
  用**仓库级覆盖** `git config --local http.proxy ""` —— 本仓库直连，其他仓库行为不变。
- 附带发现：环境变量代理 60216 能通 `ls-remote` 但 CONNECT 隧道 502，**不适合 git push**；
  直连反而更稳。大对象上传时 `http.version=HTTP/1.1` + `postBuffer=524288000`
  明显更稳（HTTP/2 多次流被重置）。
- GitHub 直连链路本身不稳（3 次 ls-remote 挂 1 次），偶发 Connection reset 属常态，重试即可。

### 后续修正：Clash Verge 实际是"在跑但出站挂了"，且代理比直连慢

上面第 30-31 行的"不动 global、改用仓库级直连"结论**方向对但归因不准**，需纠正：
- Clash Verge Rev **本来就在运行**（`clash-verge.exe` + `verge-mihomo.exe`，7897 一直在 LISTENING），
  不是"没开启"——PowerShell 的 `Get-Process`/`Get-ChildItem` 在本会话返回空输出（该工具在本环境不可靠），
  改用 Bash 的 `tasklist` / `netstat` 才查得到。**排查进程与端口一律走 Bash，PowerShell 那套会静默失败。**
- 真正故障是**节点无出站**：7897/7898/7899 转发 HTTPS 全 `000`，明文 HTTP 返回 **502**
  （502 是 Clash 自己报的出站失败，不是对端拒绝）。Clash 日志停在 8 月 → 核心长期未成功代理。
  日志目录 `~/AppData/Roaming/io.github.clash-verge-rev.clash-verge-rev/logs/`（可查 `latest.log`）。
- 用户更新订阅后 7897 恢复 200。此时实测**经 Clash 的 `git push` 反而超时**（2分36秒 exit 124，
  卡在 ls-remote 握手），**直连 1分04 秒返回 Everything up-to-date** →
  **对本仓库而言代理是负优化，保持 `http.proxy=""` 覆盖**。
- 判据记住：**代理"端口在听"≠"能出站"**。必须用 `curl -x http://127.0.0.1:7897 https://github.com`
  看是否 200，明文 HTTP 返回 502 就是节点挂了。
