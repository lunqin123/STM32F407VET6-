## Makefile 在 Windows CMD 下构建报错修复

**现象**：用户执行 VS Code "make" 任务（preLaunchTask: build）报
`子目录或文件 -p 已经存在 ... make: *** [Makefile:24: build/firmware.elf] Error 1`。

**根因**：Makefile 配方用 `mkdir -p build`（Unix 写法），但当时 make 在 **Windows CMD** 里执行配方。
CMD 的 `mkdir` 把 `-p` 当成要建的目录名 → 报"子目录或文件 -p 已经存在"。
（make 是 MinGW 版 `/d/mingw/MinGW/bin/make`；系统有 Git Bash `C:\Program Files\Git\bin\bash.exe`，其 sh 在 `/usr/bin/sh`。）

**修复（两处）**
1. `firmware/Makefile` 顶部加 `SHELL := sh` —— 强制所有配方用 POSIX shell（Git Bash 的 sh）执行，`mkdir -p` 合法。
2. `.vscode/tasks.json` 的 build 任务 `options` 加
   `"shell": { "executable": "C:\\Program Files\\Git\\bin\\bash.exe", "args": ["-c"] }`
   —— 保证 F5 / 运行任务无论用户默认终端是什么都走 Git Bash。

**验证**：Git Bash 下 `make clean && make` 通过，产出 build/firmware.elf（30640 bytes），无报错。
tasks.json 含 `//` 注释是 JSONC，VS Code 正常解析（Node 严格 JSON.parse 报注释错误属误报）。

**给用户的习惯提示**：手动在终端跑 `make` 时，请用 **Git Bash** 终端（VS Code 终端下拉选 Git Bash），别用 PowerShell/cmd，否则仍会触发该 mkdir 问题。

## RCC_AHB1ENR 时钟门控是 GPIO 配置的前提（教学）

讲清了为什么 `RCC->AHB1ENR |= GPIOxEN` 必须写在最前面：
- 复位后 RCC_AHB1ENR = 0x00000000，所有 GPIO 时钟被门控关闭（省电）。
- 时钟路径：HSI 16MHz(默认) → SYSCLK → HCLK → AHB1 总线时钟，但**每个外设单独门控**。
- 外设寄存器本质是被时钟驱动的触发器；GPIO 时钟不开，写 MODER/BSRR 没有上升沿锁存，值到不了引脚（调试里会看到 BSRR 写了但引脚不动）。
- 实践提示：使能时钟后最好读回一次或加 `__DSB()` 屏障，等时钟门控传播一拍再访问寄存器；F4 上时钟未开通常只是写不进/读全0，不会像某些系列那样直接 HardFault。
- 与上一问衔接：时钟门控在 MODER→ODR→引脚 这条数据通路的上游，是"总开关"。
- 用户位观察纠偏：其调试器里 MODER[27:26] 看到的是 0b01（bit26=1, bit27=0），属正常输出配置，无需纠结。

## PERIPHERALS 面板中文显示（工具化）

Cortex-Debug 无内置中文开关，文字全来自 SVD 的 `<name>`/`<description>`。
做法：写 `00-CHIP-REFERENCE/01-CMSIS-SVD/gen_svd_zh.py`，从原 `STM32F40x.svd` 生成双语副本 `STM32F40x_zh.svd`（把中文塞进 `<name>`="英文（中文）" 和 `<description>`="中文详解 | 原英文"），不改原文件。
`.vscode/launch.json` 的 `svdFile` 已改指 `STM32F40x_zh.svd`。覆盖 RCC 时钟使能+配置 与 所有 GPIOx 的 MODER/OTYPER/OSPEEDR/PUPDR/IDR/ODR/BSRR/LCKR（共 33 个寄存器）。
用户下次 F5 调试即可在 PERIPHERALS 看到英文旁的中文；要扩展覆盖（USART/TIM 等）改脚本字典重跑即可。

### 全量中文覆盖（用户要求"全部的都加上"）
重写 `gen_svd_zh.py`，用 共享字典 + 模式匹配 + 前缀解码 三层覆盖 **47 外设 / 884 寄存器 全部**，覆盖率 100%。
- 标准片内外设（RCC/GPIOx/USART/UART/SPI/I2C/ADC/DAC/TIM/EXTI/SYSCFG/PWR/FLASH/IWDG/WWDG/CRC/DMA/NVIC/RTC/SDIO/DCMI/RNG/DBG/FSMC/CAN）= 精心翻译的准确中文。
- USB OTG_FS/HS 与 Ethernet MAC/MMC/PTP/DMA（约 400 寄存器）= best-effort：先剥 `OTG_FS_`/`OTG_HS_`/`FS_`/`HS_` 前缀与 `_Device/_Host/_Peripheral` 后缀，再映射 HCCHAR/HCSPLT/HCINT/HCTSIZ/HCDMA/DIEP/DOEP 等通道端点，未命中走 `OTG HS寄存器 xxx` 兜底（含中文）。
- 关键坑：① 同名寄存器跨外设含义不同必须按外设分字典（如 CR 在 RCC/I2C/SPI/TIM 各异）；② 寄存器名带 bank 后缀（FSMC 的 PCR2..4、RTC 的 BKP0R..19R）要与 SVD 实际键一致；③ `<name>` 短名必须含至少一个中文字符才被算作"已汉化"，否则会被误判为未覆盖。
- 重跑命令：`py gen_svd_zh.py`（managed python）。改完 SVD 后需重新 F5 启动调试会话面板才刷新。

### 排错：Cortex-Debug 的 SVD 不会自动热更新
现象：重生成 zh.svd（884 全中文）后，PERIPHERALS 面板仍只显示旧版（RCC-only/33 个）的中文。
根因：Cortex-Debug 在**调试会话启动时**才解析 svdFile，正在运行的会话/面板会缓存旧 SVD 内容，单纯 F5 重连或 Continue 不会重新读文件。
确认文件本身正确：grep `name>MODER（端口模式）` 在 zh.svd 中存在即说明文件 OK，问题在加载侧。
解决：先 Stop 调试（红色方块/Shift+F5）彻底退出会话 → 再 F5 全新启动；仍不刷新则关掉重开 PERIPHERALS 面板，或 `Developer: Reload Window`。
兜底：若 `launch.json` 同时有 `device` 与 `svdFile` 且疑似 SVD 来源优先级冲突，临时注释 `device` 让 svdFile 单独生效（注意 device 也用于 flash 编程，排错完应恢复）。
判定经验：能显示 RCC 中文 = svdFile 路径正确已加载；"只有 RCC" = 加载的是旧缓存版，而非路径错。

### 外设级（最外层）汉化 + derivedFrom 同步
用户要求 ADC1/ADC2 等最外层外设名也带中文。在 gen_svd_zh.py 增加 `peri_cn()` + 改名阶段：
- 外设 `<name>` 改为 `原名（中文）`，并加中文 `<description>`（沿用 `annotate_text` 追加 `| 英文`）。
- **关键坑**：73 个外设有 26 个用 `derivedFrom` 继承（如 DMA1→DMA2、SPI2→SPI1、I2C1→I2C3、CAN2→CAN1、ADC2→ADC1、TIM8→TIM1）。改名时必须同步把 `derivedFrom` 属性值也映射到新中文名，否则继承类外设会丢失整组寄存器。做法：先建 原英文名→中文名 映射，再统一改名 + 改 derivedFrom。
- **另一坑**：短中文不能写成 `f"SPI{m.group(1)}"` 这类"英文重复"（如 `SPI1（SPI1）` 实际无中文字符，会被判未汉化且连累 derivedFrom）。SPI/I2C/CAN/SDIO 的短名要用真中文词（串行外设接口/集成电路总线/控制器局域网/安全数字IO）。USART/UART 用"串口1"含中文 OK。
- 顺序：寄存器阶段须先跑（此时外设名还是英文，字典才能匹配），之后再改外设名。脚本始终从原始英文 SVD 读，天然幂等。
- 结果：73/73 外设名中文、0 处 derivedFrom 未同步、884 寄存器无丢失。

### 调试时的良性 GDB 警告（本机）
现象：F5 后出现 `warning: could not convert 'main' from the host encoding (CP1252) to UTF-32` 与 `automatically using hardware breakpoints for read-only addresses`。
判定：**均无害**。前者是 GDB 在 Windows 上主机编码 CP1252 vs 内部 UTF-32 的已知 cosmetic bug（符号 'main' 为纯 ASCII）；后者因 Flash 只读、GDB 自动改用硬件断点，属预期。
证据：紧接着 `Temporary breakpoint 1, main () at src/main.c:26` 并停在 `RCC_AHB1ENR |= (1u << 2);` = 断点命中、调试链正常。
可选消除：建 `.gdbinit` 写 `set host-charset UTF-32`，并在 launch.json 加 `"debuggerArgs": ["-x", ".gdbinit"]`。一般无需处理。

用户只有 PDF 数据手册，要一个**我能读取的格式**来回答引脚映射问题。

**关键事实（F407VET6 LQFP100 引脚映射，已验证）**：

- 注意 build_flags 里**不要**加 `-D HAL_TIM_MODULE_ENABLED`（框架已定义，重复会 redefined 告警）

**坑 2 — `pio run -t compiledb` 的 compile_commands.json 不含库路径**

  生成 `.vscode/c_cpp_properties.json`（25 条 includePath）。换库后重跑一次即可。
- 验证可达性时注意：SimpleFOC 用**相对路径**引用子目录头（`#include "drivers/BLDCDriver3PWM.h"`、
  `"communication/Commander.h"`），只要 `src` 在 includePath 里就能解析——只查顶层文件名会误判"缺失"。

**VSCode 侧已配置**：`.vscode/settings.json` 加 `C_Cpp.default.compileCommands` + compilerPath；

## 加 OLED：SSD1306 0.96" I2C + U8g2（已编译验证）

**选型**：SSD1306 0.96" 128×64 **I2C 4 针**（¥6–12，3.3–5V，地址 0x3C）。
- 不用 SH1106 1.3"（显存 132×64、有 2px 列偏移，需换构造函数）、不用 SPI 版（多占 GPIO）、不用 TFT（库重）、不用 1602（只能 2×16 字符且体积大）。
- 库选 **U8g2 2.36.18**（非 Adafruit_SSD1306）：零额外依赖（Adafruit 要拖 GFX+BusIO）、同一份代码兼容 SSD1306/SH1106、有 U8X8 省 RAM 模式。
- 构造函数：`U8G2_SSD1306_128X64_NONAME_F_HW_I2C u8g2(U8G2_R0, U8X8_PIN_NONE)`（`_F_`=全缓冲 1KB RAM）。

**⚠️ 更正此前记录：F407 的 Wire 引脚是 PB7=SDA / PB6=SCL（不是反过来）**
- 实测依据：`framework-arduinoststm32/variants/STM32F4xx/F407V(E-G)T_F417V(E-G)T/variant_generic.h` 第 184–188 行 `PIN_WIRE_SDA=PB7` / `PIN_WIRE_SCL=PB6`。
- 大量网贴按 UNO 习惯写 PB6=SDA/PB7=SCL，在 F4 上是**反的**，接反屏幕全黑（不烧）。
- 代码里显式 `Wire.setSDA(PB7); Wire.setSCL(PB6);` **必须在 `Wire.begin()` / `u8g2.begin()` 之前**调用（U8g2 内部会再调一次 Wire.begin()，重复无害）。

## 坑 4 — C_Cpp.default.compileCommands 会让 IntelliSense 忽略正确的 includePath（接坑 2）

**现象（用户报）**：`无法打开源文件 "U8g2lib.h"`（SimpleFOC.h 同理会红）。编译本身 `pio run` 一直通过。

**根因（比坑 2 更隐蔽）**：坑 2 修了 `compile_commands.json` 缺库路径、改由 `gen_intellisense.py` 生成带全量路径的 `c_cpp_properties.json`。
**但 `.vscode/settings.json` 里当时还留着 `C_Cpp.default.compileCommands` 指向那份缺库的 `compile_commands.json`**。
VS Code C/C++ 扩展的行为是：**一旦对某文件设了 compileCommands 且该文件在数据库里，就优先用数据库里的 include/defines，完全忽略 `c_cpp_properties.json` 的 `includePath`**。
于是 `c_cpp_properties.json` 里那条正确的 `U8g2\src` 路径根本没被用到 → `U8g2lib.h` 必红。

**判定线索**：`c_cpp_properties.json` 的 includePath 已含 `U8g2\src`（grep 能查到），但编辑框仍报红 → 说明扩展没在用这份 includePath，被 compileCommands 截胡了。

**解决（两步）**：
1. **删掉 `settings.json` 里的 `C_Cpp.default.compileCommands`**（连同注释）。让扩展只走 `c_cpp_properties.json` 的 includePath（已含框架+libdeps+框架自带库，共 41 条）。`settings.json` 只保留 compilerPath / 标准 / defines。
2. `gen_intellisense.py` 增强：把硬编码 `ENV="genericSTM32F407VET6"` 改成**扫描 `.pio/libdeps` 下所有环境**（`selftest` 等多环境通用）；includePath 39→41 条；递归校验 7 个头文件（Arduino/Wire/SimpleFOC/BLDCMotor/BLDCDriver3PWM/Commander/U8g2lib）全部 OK。
3. 用户侧：VSCode 执行 `C/C++: 重置 IntelliSense 数据库` + `Developer: Reload Window`（让新的 settings.json 生效）。

**结论 / 防复发**：PlatformIO + VS Code 的 IntelliSense 正确姿势 =
- **绝不设** `C_Cpp.default.compileCommands`（那是坑，因为 compiledb 缺库路径）；
- **只靠** `gen_intellisense.py` 生成的 `c_cpp_properties.json` 提供全量 includePath。
- `errorSquiggles` 若用户层设为 enabled，移除 compileCommands 后红线自然消失；workspace 里当前是 "disabled"（减少 HAL 宏噪音）。

**新增环境（自检固件 `selftest`）**：`platformio.ini` 已是双 env（`genericSTM32F407VET6` 跑电机 + `selftest` 到货自检）。`gen_intellisense.py` 现在两 env 都扫，避免以后再加 env 又漏路径。

## 关键坑：本沙箱编译用 vendor 库模式（坑5，区别于坑4）

本沙箱里 `pio run` 会因「安全删除拦截」在新机器上装不了 lib_deps：
1. 沙箱把整个 `~/.platformio/.cache` 子树（~1902 文件，含 10 个 `pkg-installing-*` 陈旧临时目录）当"删除作用域"，PlatformIO 安装库时的清理步骤被永久阻断 → install 直接 exit 1，连编译都进不去。
2. 之前成功编译 main/selftest 是因为那时 `.pio/libdeps` 已存在、跳过 install；删了 `.pio` 后所有环境都触发 install → 全挂。

**修法（已落地，且对用户在真机也通用）**：把 SimpleFOC / U8g2 解包进项目 `lib/`（PIO 自动扫描 `lib/`，无需 lib_deps install，零删除、可离线）。
- ⚠️ 抓缓存时抓错版本：`.cache/tmp/pkg-installing-08loabay` 实为 **SimpleFOC 2.4.0**（其 `stm32_mcu.cpp:126` 调 `enableTimerClock(TIM_HandleTypeDef*)`，与 framework-arduinoststm32 4.30000.0 的 `enableTimerClock(TIM_TypeDef*)` 不兼容 → 编译报 cannot convert）；正确应是 `pkg-installing-rsvjpe4s` = **2.3.4**（根本不调 enableTimerClock，避开签名问题）。
- 教训：vendor 前先 `grep version library.properties` 确认版本，别凭目录名。
- `platformio.ini` 已去掉 `lib_deps`，改注释说明库在 `lib/`（并保留"想换回联网 lib_deps 取消注释即可"的说明）。这个改动在用户真机上也能编译（lib/ 优先级高于 lib_deps），且更利于离线/可复现。
