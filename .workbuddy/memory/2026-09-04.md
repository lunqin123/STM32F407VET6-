## ★★ 关键坑：STM32 USB CDC 必须 setDTR(True)
- **现象**：COM8 能枚举（VID:PID = **0483:5740** = STMicroelectronics Virtual COM Port），命令也发出去了（TX 成功），但**收到 0 字节**，固件毫无反应。
- **根因**：脚本里写了 `ser.setDTR(False)`。STM32 的 USB CDC 靠 **DTR 判断主机是否就绪**，DTR 为低时固件不发数据。
- **解法**：`ser.setDTR(True)` + `ser.setRTS(False)` + sleep(1.0)。已固化进 `tools/serial_capture.py`。
- **通用判据**：只要 COM 口出现且 VID:PID = 0483:5740，硬件链路就是通的；此时零字节 ⇒ 100% 是 DTR 问题，不要去怀疑波特率或数据线（USB CDC 的波特率是虚设的，任意值都能通）。

## ⚠️ 事故：12V 反接（严重，需持续跟进）
- **事件**：用户把 12V 适配器正负极反接到 Shield 的 VCC/GND 端子，随后正确重接，电机无反应。
- **危险电流路径（务必记住）**：适配器正极 → Shield GND 端子 →**共地线** → F407 GND → F407 USB 口 GND → USB 线 → 电脑主板地 → 回到适配器负极。**等于 12V 直接对地短路，几乎不限流。**
- **根本原因**：F407 与 Shield 共地（本来是必须的），反接时把 F407 的整个地平面抬到 +12V，而 F407 同时经 USB 接电脑（0V）。
- **当前现象**：适配器输出仅 **0.4V** → 判断为**过流保护关断（打嗝模式）**，是残余/洩放电压，不是"部分损坏"。
- **这是好消息**：适配器保护动作说明反接电流被限制，下游（Shield / F407 / 电脑 USB 口）**幸存概率高**。
- **验证方法**：适配器**完全拔掉负载**，静置 30 秒以上，再空载量输出端。恢复 12V = 只是触发保护；仍 0.4V = 适配器已烧毁需更换。
- **隔离排查顺序（已下发用户）**：① 断电 ② 查烧痕/异味/发烫 ③ 先确认**电脑 USB 口**仍正常 ④ **断开 F407 与 Shield 全部连线**后单独测 F407 ⑤ 空载测适配器。
- **铁律**：在第 ④ 步确认 F407 完好前，不得让 Shield 与 F407 重新相连，不得上 12V。

## ★★ "OLED 只有 deg 没有数字" 案：newlib-nano 裁剪了 printf %f
- **表象**：用户报 "OLED 显示的都是 deg"、"没有显示任何值"。
- **排查链**（价值高，记录方法论）：
  1. 先验 loop 是否存活：发 `M2` 有响应 → command.run() 正常 → 不是死机
  2. 写 `as5600test.cpp` 直读 AS5600 寄存器 → `RAW=3266 ( deg)` ← **诊断固件自己暴露了 %f 输出为空！**

  4. 根因：**stm32duino 默认 newlib-nano，printf/snprintf 的 %f 被裁剪输出为空**。`Serial.print(float)` 是 C++ 重载不受影响，所以 selftest 没暴露；gimbal/main 的 OLED 用 snprintf %f → 全空

- **★ PIO 大坑**：写 `-u _printf_float` 会被 PIO 拆成孤立 `-u`（`_printf_float` 被当库依赖挪走）→ 孤立 `-u` 吞掉后面的 `-mcpu=cortex-m4` → CMSIS 报 `#error "Unknown Arm architecture profile"`。**必须用 `-Wl,-u,_printf_float` 单 token 写法。**
- 已验证：修复后 `(287.1 deg)` 正常输出；gimbal 固件已重烧（72.8s）。
- 影响面：main.cpp / closedloop.cpp 的 OLED 也用 %f —— 全局 flags 已修，后续重编自动生效。
- 待用户最终验收：OLED 三行应有数字，手转电机轴 Now 平滑跟随（AS5600 角度链路收官）。

## ★ "Now 恒 0" 案：SimpleFOC 缓存机制，非硬件故障
- 用户修复 %f 后回报：OLED 有数字了，但**转电机轴 Now 恒 0**。
- **根因**：`motor.shaftAngle()` 返回的是 loopFOC 维护的**缓存** shaft_angle，而 `loopFOC()` 第一道门是"initFOC 电角度对齐成功"。**无 12V → 对齐失败 → loopFOC 每圈直接 return → 缓存永不更新 → 恒 0**（上电时轴的 RAW≠0 也没用，显示的是缓存）。这与 AS5600 硬件无关（诊断固件已证 RAW=3266/287.1° 有效）。
- **修复**：`gimbal_tracker.cpp` drawOLED 的 Now/Err 改用 **`sensor.getAngle()` 直读 AS5600**（Sensor 基类接口，不经 loopFOC 缓存），无 12V 也能手转轴联调。已重烧（61.8s）。
- **通用教训**：SimpleFOC 中凡是"无动力时也想要读数"的场景（显示/记录/无动力联调），必须直读 `sensor.getAngle()`，不能用 `motor.shaftAngle()`/`motor.shaftVelocity()`。12V 上电 initFOC 成功后两者一致。
- 待用户：转轴看 Now 平滑跟随 → P1 硬件验证收官。
- **追加**：用户转轴后 Now 会持续累加到 ±∞ 而非循环 —— 这证明角度实时跟手了（好事），但 `sensor.getAngle()` 是**带累计圈数的连续角**。改用 **`sensor.getMechanicalAngle()`（单圈 0~2π wrap）** 即循环显示。已重烧。**SimpleFOC 传感器 API 区别**：getAngle()=连续多圈角 / getMechanicalAngle()=单圈角 / getSensorAngle()=原始角。

## ① 旋钮 bug 修复 + ② 增量编译策略（用户两问的答案）
### 旋钮没反应的根因：整数量化丢精度
- 原代码每帧 `knob += (int)roundf(d * k)` —— 100Hz 下慢转时每帧增量 < 0.5 单位，roundf 全归零 → "转了没反应"。

- 待用户验证。

### 编译时间：日常必须用增量，不要 rm
- **实测**：改单个 .cpp 后不清理直接编译 = **15.8 秒**（对比全量 80s）；`-t nobuild -t upload` 纯烧录 = **8.8 秒**。

## ★★ SimpleFOC 核心：Sensor 是 pull 模型（knob 第二次修复）
- 用户回报浮点累加修复后**仍然无变化** → 真根因浮出：
- **SimpleFOC 所有 getter（getMechanicalAngle/getAngle/getVelocity）返回的都是内部缓存，必须有人调 `sensor.update()` 才真正读芯片。**
- knob 固件没有 motor（没人调 loopFOC→update）→ 缓存上电起就是 0 → 恒 50 不变。
- gimbal 固件能跟手是因为 loop 里 `motor.loopFOC()` 每圈在调 sensor->update()。
- **修复**：knob loop 开头加 `sensor.update()`；setup 里 sensor.init() 后也先 update() 一次再取 last_raw。已烧录（Flash 61256B）。
- **★ 推论修正**：之前记的"sensor.getAngle() 直读芯片绕开缓存"是**错的** —— 它也是缓存。gimbal 无 12V 时能跟手，是因为 loopFOC 在无 12V 下依然会执行到 sensor->update()（只是 FOC 计算不完整），而不是"绕开了缓存"。正确表述：**有 loopFOC 在跑 = 缓存自动更新；没有 motor = 必须自己调 update()。**
- 通用规则：**任何不含 motor.loopFOC() 的固件里用 SimpleFOC 传感器，都必须自己每帧调 sensor.update()。**

## ★ 社区 haptic knob 实现调研（用户批评后补课：有现成参考却自己造轮子，连出两 bug）
- **用户旋钮已验证工作**。随后调研 SimpleFOC 社区实现，核心来源：community.simplefoc.com/t/301（schoch 的 haptic textures / virtual detents）+ scottbez1/smartknob README。
- **社区 detent 核心公式（schoch，极简）**：torque 模式下三行代码
  1. 量化到最近刻度：`attractor = round(angle / dist) * dist`（dist=30°→8 档）
  2. 纯 P 弹簧拉向刻度：`motor.move(P * (attractor - shaft_angle))`，P=10~40（刚度=手感强弱）
  3. `motor.torque_controller = voltage` + `motor.controller = torque`；`limit` 限力矩（4~12）
- **手感配方**：多档刚度 PID（weak/mid/strong）区分档位类型；**阻尼** = 力矩与速度反向（或 velocity 模式 target=0，只在超阈值时施加）；**边界墙** = 越界时刚度猛增。schoch 还做了 4 档虚拟拨动开关（带"click"感）。
- **smartknob（Scott Bezek）架构级经验**：闭环扭矩反馈动态生成 detent/endstop；**编码器噪声会被 PID 微分项放大成可闻/可感的嗡嗡声 → 必须滤波**；硬件选型排序 MT6701 >> AS5600（"mediocre"：噪声大、易饱和）+ TMC6300 + 空心轴低齿槽云台电机；固件分电机控制/日志/protobuf 串口协议/主机库四层。
- **对本项目硬件的适配评估**：C2208 空心轴低齿槽云台电机 = 理想（与 smartknob 推荐同型）；**AS5600 是短板**（I2C 读数慢 ~1kHz + 噪声大），做入门 detent 够用，追求手感后续换 MT6701（SSI 接口，也兼容 I2C 升级路径）；DRV8313 Shield 跑 voltage-torque 模式无压力。
- **升级路径评估**：knob.cpp 角度跟踪 + 社区三行力控 ≈ 再写 ~15 行即可做 8 档棘轮；起步参数 dist=30°、P=10、limit=2V（安全）。**未改代码（遵用户指示），12V 到手后作为第一个力控实验。**
- **教训（方法论）**：有社区经典实现时必须先读实现再动手 —— 自研连出两个 bug（取整丢步、pull 模型漏 update），社区代码里根本不存在这两个坑。
